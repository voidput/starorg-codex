# StarOrg Strings v1

StarOrg Strings is a desktop app and command-line tool that customises Star Citizen's
localization file. It reads the installed `Data.p4k`, builds an enhanced `global.ini`
(stat blocks, name tags, mission and blueprint info, fixes for known CIG text bugs) and
applies it to the game per channel, with backups and rollback.

It is part of StarOrg Tools (starorg.tools). Repo: `voidput/starorg-strings`.

**Credits.**

- Feature ideas come from [Smart Citizen](https://github.com/Osiris-DevWorks/smart-citizen) by Osiris
  DevWorks (Apache-2.0). We use it as a source of ideas only. No Smart Citizen code is
  copied; this spec describes behaviour and output formats so they can be written fresh.
- Game data reading uses the [StarBreaker](https://github.com/diogotr7/StarBreaker) crates
  by diogotr7 (MIT), as a library.
- Design language comes from our own RSI+ and StarOrg Tools apps.

Status: draft, revision 2 (see the review log at the end). Frontmatter is generated by
`scripts/obsidian_frontmatter.py`.

Related notes: [addendum with later user requests](starorg-strings-v1-addendum.md) (published
data dumps as a data source, launcher hooks, owned-blueprint tracking). Its direction is
settled in sections 3.4, 8 and 11. Q17 (decided 2026-11-14) put the features in v1: the hook

## 1. Goal and non-goals

### Goal

One native app, Rust only on the backend, that does the following on Windows and Linux:

1. Applies an enhanced `global.ini` per game channel, with backups, validation and rollback.
2. Adds stat blocks and name tags for ships, ship components, ship weapons, FPS weapons and
   missiles.
3. Adds mission and blueprint info to contract titles and descriptions.
4. Fixes known CIG data bugs through our own patch system.
5. Runs headless: `starorg-strings apply --channel LIVE`, usable from
   `~/git/sc-setup/prefix/sc-prelaunch.sh`.
6. Installs easily: one installer on Windows, deb/rpm/AppImage on Linux, signed updates,
   network off until the user turns it on.
7. Can always be undone: one action puts a channel back to the stock game text.

### Non-goals for v1

- Parity with Smart Citizen's output. Its output contains bugs (section 15.2). Our golden
  tests come from this spec.
- Non-English game languages and community language overlays. v1 writes English only. A
  channel set to another language is left alone unless the user agrees to switch it
  (section 7.4). The data model keeps a language field so this can be added.
- Commodity, mining, journal and medical enhancements. They need curated or third-party
  tables (resource signatures, effect texts).
- Mission route-in-title, title shortening, hostile/friendly spawn breakdown and engagement
  type. All of these rest on keyword tables.
- Overlay/OCR, shader cache cleaning, guided tour, loc-pack export.
- Flatpak and macOS builds.
- Any telemetry, ever.
- Editing game files other than `global.ini` and one line of `user.cfg`. We never write
  `Data.p4k` and never write `languages.ini`.
- ~~An installer for launcher hooks (`hook install`) and owned-blueprint tracking.~~ Moved
  into v1 by Q17 (M1, addendum §2-§4).

## 2. Users and install story

### Users

- **Player (most users).** Installs, runs the setup wizard, clicks Apply, re-applies after a
  game patch. Never opens the advanced pages.
- **Power user.** Tunes which stats show, edits single strings, writes patches, browses the
  full string table.
- **Scripter (us).** Runs the CLI from a launch hook. No window, no display needed.

### Two binaries, same names on both systems

| Binary | What it is | Links GTK / WebView |
|---|---|---|
| `starorg-strings` (`.exe` on Windows) | The CLI. Console program. Also runs the hidden `extract-worker` step | No |
| `starorg-strings-app` (`StarOrg Strings.exe` on Windows) | The GUI (Tauri) | Yes |

The CLI is a separate small binary on **both** systems. It starts without WebKitGTK or
WebView2 installed, and its start-up time is not affected by the GUI's libraries.
`starorg-strings gui` starts the app when it is installed next to it.

### Windows

- One NSIS installer, `StarOrg-Strings_<version>_x64-setup.exe`, per-user install
  (`%LOCALAPPDATA%`, no admin prompt). It contains both binaries.
- A portable zip, `starorg-strings_<version>_windows-x64.zip`, with the same two binaries, for
  people who do not want an installer. It does not self-update.
- The installer offers "Add the command-line tool to PATH" (per-user `HKCU\Environment`,
  default on, removed again on uninstall).
- WebView2: Windows 10 1803+ and 11 ship the runtime. The installer embeds the small
  bootstrapper, which downloads the runtime **only when it is missing**. This is the one case
  where installing needs the network, and the installer page says so.
- **Not signed in v0.x.** What that means, stated in the README and on the download page:
  - SmartScreen shows "Windows protected your PC"; the user picks More info → Run anyway.
  - With **Smart App Control** on (some Windows 11 installs), unsigned programs do not run and
    there is no per-app bypass. Those users cannot use v0.x. Signing is the only fix (Q3).
  - Unsigned Rust/NSIS programs sometimes get antivirus false positives. We submit each
    release to Microsoft's file analysis and publish `SHA256SUMS` signed with our release key.
- **Game folder permissions.** The default library is under `C:\Program Files`. We never
  elevate. Before the first write the app does a write probe in the target folder
  (section 7.1). If it is denied, the app explains the two ways out and stops: move the
  library to a user-writable folder in the RSI Launcher, or run one shown `icacls` command in
  an administrator terminal that gives the current user Modify rights on
  `<channel>\data\Localization` and on `user.cfg`. Whether a default install is writable is
  checked on a real Windows install in M1 (section 14).
- **Uninstall.** The uninstaller has a ticked box "Also remove StarOrg text from the game". It
  runs `starorg-strings remove --all --yes` first, which puts every set-up channel back to
  stock (section 7.6). App data (profiles, backups) is kept unless a second box is ticked.
- Updates: in-app, signed with the Tauri updater key, only after the user enables
  "Check for updates".

### Linux

| Package | Installs | Updates | For |
|---|---|---|---|
| deb, rpm | `/usr/bin/starorg-strings` (CLI), `/usr/bin/starorg-strings-app` (GUI), desktop entry. GUI uses the system `webkit2gtk-4.1` | Package manager; the app only tells you a new version exists | Debian/Ubuntu, Fedora |
| AUR `starorg-strings-bin` | Same files, repackaged from the deb | AUR helper | Arch, CachyOS (recommended there) |
| AppImage | The GUI with WebKit bundled. Contains the CLI too | Self-updating | Atomic systems (SteamOS, Bazzite) and anything else |
| CLI tarball `starorg-strings-cli_<version>_linux-x86_64.tar.gz` | One static (musl) binary | Manual | Hooks on systems that use the AppImage, servers, scripts |

- **CLI for AppImage users.** Settings → Command line → **Install command-line tool** copies
  the bundled CLI to `~/.local/bin/starorg-strings` (and updates it after each app update).
  Hooks never call the AppImage itself, so no FUSE mount per call.
- The app runs natively. It does not need Wine and does not touch the Wine prefix's registry
  or wineserver.
- **Uninstall.** Packages cannot run per-user steps. The README and the app's Settings page
  say: run `starorg-strings remove --all` before uninstalling. `doctor` (also in the CLI
  tarball) can do it later, because the state it needs is in the app data folder.

### What must be decided before any package is built

Everything public depends on **where releases are published** (Q1): the updater endpoint and
public key are baked into v0.1.0, the AUR package needs a public source URL, the "new version
exists" check needs a public file, and README download links must work without a GitHub
login. This spec assumes a **public `voidput/starorg-strings-releases` repo** that holds only
binaries, `latest.json`, `SHA256SUMS`, the PKGBUILD and install notes, while the source repo
stays private. The decision is due at the end of M0, before any packaging work.

## 3. Architecture

### 3.1 Workspace layout

```
starorg-strings/
  Cargo.toml                  workspace; [workspace.package] version is the single version;
                              [profile.release] panic = "unwind" (required, see 3.3)
  rust-toolchain.toml         pinned stable (1.92 or newer, required by StarBreaker's deps)
  crates/
    starorg-data/             the ONLY crate that depends on StarBreaker
    starorg-core/             ini, model, generators, patches, merge, apply, backups, discovery
    starorg-cli/              clap commands; lib `run(args) -> ExitCode`; bin `starorg-strings`
  app/
    src-tauri/                Tauri 2 shell; bin `starorg-strings-app`; thin commands over starorg-core
    src/                      Svelte 5 + Tailwind 4 + shadcn-svelte UI
  patches/                    built-in patch files (*.patch.toml), embedded at build time
  fixtures/                   recorded test fixtures (section 13); no CIG prose
  docs/                       repo vault
  scripts/                    obsidian_frontmatter.py, release helpers
```

| Crate | Owns | Depends on |
|---|---|---|
| `starorg-data` | Open `Data.p4k`, check the entry count, read `global.ini` and `Game2.dcb`, run DataCore queries, fill the `GameData` model, report schema drift | starbreaker-p4k, starbreaker-datacore, starbreaker-common |
| `starorg-core` | `GameData` model, `GameSource` trait, INI reader/writer, generators, patch engine, merge, validation, apply/backup/restore, install discovery, config, app directories | serde, toml, rayon, directories; `starorg-data` only behind the `GameSource` trait |
| `starorg-cli` | Argument parsing, human and JSON output, exit codes, the `extract-worker` step | `starorg-core`, `starorg-data` |
| `app/src-tauri` | Window, Tauri commands, progress events, updater | `starorg-core` |

Rules:

- No UI crate and no generator talks to StarBreaker directly. A StarBreaker rev bump touches
  `starorg-data` only.
- `starorg-core` and `starorg-cli` do not link GTK, Tauri or any HTTP client. CI checks this
  with `cargo tree`.
- GUI and CLI use the same app directories, resolved with the `directories` crate, not with
  Tauri's `AppHandle`.
- The GUI never extracts in its own process. It starts the CLI binary that ships next to it
  (section 3.3).
- The release profile keeps `panic = "unwind"`. Tauri size guides suggest `abort`; we do not
  follow that, and a CI test fails if the profile changes.

### 3.2 Data flow

```
discover channels
      |
      v
extract (worker process)           Data.p4k --> stock global.ini bytes (BOM, CRLF)
      |                                     --> Game2.dcb bytes --> DataCore queries
      v
GameData (normalised model)  <---- data patches applied as an in-memory overlay
      |
      v
enhancement generators (pure functions: GameData + stock strings + profile --> edits)
      |
      v
merge:  stock  <  generated edits  <  loc patches  <  user overrides
      |
      v
render: stream stock lines, replace values only  -->  validate (drop bad edits)
      |
      v
backup  -->  user.cfg line if needed  -->  journal  -->  atomic write  -->  verify  -->  record
```

Each step is a function with plain inputs and outputs, so it can be tested without a game
install:

- `extract(channel) -> Extraction { base_ini: Vec<u8>, game_data: GameData, fingerprint }`
- `apply_data_patches(&mut GameData, &[Patch]) -> Vec<PatchOutcome>`
- `generate(&GameData, &StockStrings, &Profile) -> Vec<Edit>`
- `merge(stock, edits, loc_patches, overrides) -> Merged` (keeps provenance per key)
- `render(&base_ini, &Merged) -> Vec<u8>`
- `validate(&base_ini, &mut Merged) -> Validation { dropped, file_errors }`
- `apply(channel, output) -> ApplyReport`

An `Edit` is `{ key, new_value, source: EditSource, record: Option<RecordRef> }`. Provenance
is kept through the merge so the UI and `--json` output can say why a string changed.

### 3.3 Extraction details (`starorg-data`)

**StarBreaker revision.** Everything in this spec was tested against upstream
`diogotr7/StarBreaker` commit `041e559215e18e1b13b124cab0e3ecb0f3aa50d4` (origin/main,
2026-11-14). The numbers quoted (open about 0.4 s warm, peak about 890 MB) belong to that
commit. The local checkout `~/git/StarBreaker` is older (`08302fbd`, 804 commits behind): it
does not have the silent-stop behaviour described below and its `LICENSE` file is only the
word "MIT". The pinned commit has the full MIT text ("Copyright (c) 2026 Diogo Trindade"),
which is what we ship. We depend on our own mirror, `voidput/StarBreaker`, at that same
commit, so an upstream force-push or deletion cannot break our builds
([ADR](../../decisions/starbreaker-as-library.md)).

**Extraction runs in a child process.** The parent (GUI, or `starorg-strings apply`) starts
`starorg-strings extract-worker --p4k <path> --out <cache dir>` and waits for it.

- A crash of any kind in the worker (panic, out-of-memory abort, stack overflow) is an exit
  status for the parent, not a crash of the app or of the launch hook.
- All memory (about 890 MB at peak) is returned when the worker exits. A machine-wide advisory
  lock (`locks/extract.lock`) allows one worker at a time, so the GUI and a hook cannot both
  hold that much.
- The parent enforces the time budget (`--timeout`) by killing the worker.
- Inside the worker, DataCore work still runs under `catch_unwind` so a panic becomes a
  readable error message. This needs `panic = "unwind"` (section 3.1); a release-mode test
  panics inside the worker on purpose and checks the parent reports it.

Steps inside the worker:

1. `MappedP4k::open(<channel>/Data.p4k)`.
2. **Entry-count check.** In the pinned commit, `parse_entries` stops without an error when
   an entry after the first fails to parse (upstream commit `dd7a6095`, meant for embedded
   `.pak` archives whose stored count is wrong). A new CIG extra-field tag would therefore
   silently hide every later entry. StarBreaker keeps its count and locator code private, so
   `starorg-data` has its own small reader (`eocd.rs`, about 60 lines) for the fixed-layout
   end-of-central-directory, ZIP64 locator and ZIP64 end record. It reads `total_entries` and
   the worker fails if `p4k.len()` differs.
   - This duplicates a little of StarBreaker's parser. It is kept to those three fixed
     structs and unit-tested against hand-built byte tails. It needs no synthetic archive.
   - If the tail is the newer "p4k v2" container, the reader does not know the count. Then
     the check is replaced by the weaker ones in step 3 plus a warning. v2 support in
     `eocd.rs` is added when a channel actually uses it.
   - Upstream gets a pull request for an **opt-in** strict mode (stale counts are legitimate
     for embedded archives, so not a revert) (Q2).
3. Read `Data\Localization\english\global.ini` and `Data\Game2.dcb`. Both must exist. Declared
   uncompressed sizes are checked before allocating (ini at most 64 MiB, DCB at most 2 GiB).
   The CRC-32 from each entry is checked against the bytes read. `Data\Game.dcb` is used only
   when `Game2.dcb` is absent from an archive that passed step 2.
4. Drop the p4k handle (frees about 400 MB of index) before parsing the DataCore.
5. `Database::from_bytes`, compile every query path once, run the queries with rayon, fill
   `GameData`.
6. A path that fails to compile, or a query that returns nothing for a record type that had
   results in the recorded fixture, is a **schema-drift warning** naming the stat it feeds.
   The stat is left out; the build continues; the apply result carries the warning
   (exit code 5, section 8).
7. Write the cache entry atomically (section 4.2) and exit.

Entry names inside the p4k use backslashes. They are written as string literals, never built
with `Path::join`.

### 3.4 `GameData`: the internal model

Generators read one normalised model, not DataCore. It holds only what v1 needs:

- `items`: record name, GUID, DataForge path, AttachDef type/subtype/size/grade/manufacturer,
  loc key references (`name_key`, `short_name_key`, `desc_key`), and typed stat structs
  (shield, quantum drive, power plant, cooler, radar, weapon, missile, armor, ...).
- `ammo`, `ships` (with resolved default loadout and flight controller), `contracts`,
  `blueprints`, `blueprint_pools`, `reputation_standings`.
- `build`: branch, game version, change number, launcher version string (section 4.1).
- `schema`: the model layout version, bumped whenever a field changes meaning.

Why a model in between:

- Data patches address stable field names, not query paths (section 4.5).
- Generators are pure functions that golden tests can feed from a recorded fixture.
- More than one source can fill it.

**`GameSource` trait** (in `starorg-core`, designed in M0 with both sources in mind):

```rust
trait GameSource {
    fn load(&self, channel: &Channel, budget: &Budget) -> Result<Loaded, SourceError>;
}
struct Loaded { base_ini: Vec<u8>, game_data: GameData, origin: Origin, warnings: Vec<Warning> }
```

- `LocalExtraction` (v1): the worker in section 3.3. Always available, needs no network, and
  is complete on its own. With network consent off (the default) it is the only source.
- `PublishedDump` (addendum; v1 per Q17, M2): downloads datasets from
  `voidput/sc-gamedata-dumps` for the exact build. The user asked for this to be tried first
  **when the user has turned that network feature on**; local extraction is the fallback.
  Dumps never contain the English text, so `base_ini` always comes from the local `Data.p4k`.

`GameData` is serialisable (serde). It is cached per build fingerprint, and a recorded copy
is the main test fixture.

## 4. Data model

### 4.1 Channels and installs

- An **install** is a game library root, e.g.
  `<prefix>/drive_c/Program Files/Roberts Space Industries/StarCitizen`.
- A **channel** is any direct subdirectory of an install that contains `Data.p4k`. Known names
  are `LIVE`, `HOTFIX`, `PTU`, `EPTU`, `TECH-PREVIEW`; unknown names are accepted. Our machine
  has LIVE, HOTFIX and PTU.
- **Build identity** comes from `<channel>/build_manifest.id` (JSON):

| Field | LIVE here | HOTFIX here | Used for |
|---|---|---|---|
| `Data.Branch` | `sc-alpha-4.10.0` | `sc-alpha-4.10.0-hotfix` | **Game version**: the first `major.minor[.patch]` in the string, compared as three numbers (missing patch = 0). Here both are 4.10.0 |
| `Data.RequestedP4ChangeNum` | `13165946` | (per build) | **Change number**: one counter across all branches. Identifies the exact build |
| `Data.Version` | `4.10.200.58746` | `1.0.191.55227` | Display only. It is numbered per branch and is **never compared** |

  If `Branch` has no version in it, the game version is "unknown": build ranges are not
  enforced (a warning says so) and only `expect` guards protect patches.
- **Fingerprint** of the game data: change number + `Data.p4k` size + `Data.p4k` mtime.
- A channel is **set up** when its state file has `consent = true`. The wizard or
  `starorg-strings setup` sets it. Nothing writes into a channel that is not set up
  (section 8).
- Game files we touch, per channel. Every path component is resolved case-insensitively
  against what is on disk (section 10.3), and symlinks are followed, never replaced
  (section 7.4):
  - `Data/Localization/english/global.ini` (written or deleted)
  - `user.cfg` (one line, only when needed)

### 4.2 App directories

| Purpose | Linux | Windows |
|---|---|---|
| Config | `~/.config/starorg-strings/` | `%APPDATA%\StarOrg Tools\Strings\config\` |
| Data | `~/.local/share/starorg-strings/` | `%APPDATA%\StarOrg Tools\Strings\data\` |
| Cache | `~/.cache/starorg-strings/` | `%LOCALAPPDATA%\StarOrg Tools\Strings\cache\` |

```
config/
  config.toml                         installs (id, last known path), default channel,
                                      appearance, network consent switches
data/
  outputs.json                        every output we ever wrote: sha256, install id, channel,
                                      change number, time (newest 200)
  patches/*.patch.toml                the user's own patches (all channels)
  cfg/<hash of real path>.json        what we changed in one user.cfg (section 7.4)
  locks/                              channel, user.cfg and extraction lock files
  channels/<install-id>/<CHANNEL>/
    channel.toml                      consent, language decision, set-up time
    profile.toml                      enhancement settings for this channel
    overrides.ini                     user string overrides
    applied.json                      what the last apply wrote and from which inputs
    intent.json                       journal of an apply in progress (section 7.1)
    backups/<timestamp>-<reason>/     section 4.6
  logs/
cache/
  <install-id>/<CHANNEL>/<cache-key>/
    meta.json                         key inputs + sha256 of the two files below
    base.ini                          stock global.ini, byte for byte
    gamedata.json.zst                 serialised GameData
```

**Install id.** A random id created when an install is first seen, stored in `config.toml`
with its last known canonical path. It is not derived from the path, so moving or remounting
a prefix, or a Windows drive-letter change, does not orphan the profile, overrides and
backups.

- **Re-link.** When discovery finds an install at an unknown path, and a stored install's
  path no longer exists, the two are matched if a loose `global.ini` there is in
  `outputs.json`, or the channel names and change numbers equal the stored ones. The CLI
  re-links by itself only on an `outputs.json` match. The GUI asks "Is this the same install,
  moved?" for the weaker match.
- **Knowing our own output.** A loose `global.ini` whose SHA-256 is in `outputs.json` is ours,
  whatever the install id or `applied.json` say. This keeps our own file from being treated
  as another tool's, or backed up as "the file from before StarOrg Strings".

**Cache.** `<cache-key>` is a hash of: fingerprint, `GameData` schema number, StarBreaker
commit, and the source (`local` or `dump`). An app update that changes the model layout
therefore never reads an old cache.

- Written into `<cache-key>.tmp-<pid>/`, files fsynced, then the directory is renamed.
- On every load, `meta.json` is read and both files are hashed and compared. A mismatch
  deletes the entry and extracts again.
- `base.ini` must start with the BOM and hold at least 50,000 keys, or it is rejected. This
  matters because validation (section 7.3) compares output against this same file.

Nothing of ours is stored inside the game directory, so the launcher's "Verify files" cannot
remove it.

### 4.3 Sources and merge order

Lowest to highest priority:

1. **Stock**: the English `global.ini` read from `Data.p4k`. Never the loose file in the game
   directory, which may have been written by us or by another tool.
2. **Generated**: edits from the enabled enhancement generators.
3. **Loc patches**: string-level patches (section 4.5).
4. **User overrides**: `overrides.ini`.

Within "generated", generators run in a fixed order and each key has one owner (section 5.1),
so two generators never fight over a key. Name tags and stat blocks touch different keys
(name vs description).

An edit is kept in parts (`prefix`, `stock`, `suffix`, or `whole`) until render time, so
validation knows exactly which text we added (section 7.3) and patches can ask for "the
generated part" of a key.

**Matching a referenced key to a stock key.** DataCore gives loc references with a leading
`@`, and CIG's casing there often differs from `global.ini`. The game looks keys up without
regard to case. So:

- Strip the `@`. Fold case. Ignore a flag suffix such as `,P` on the stock side.
- The index is built once: folded key → stock line. On LIVE 4.10 no two of the 90,363 stock
  keys collide after folding. If two ever do, both are left out of generation and reported.
- The same matching is used for patch keys and override keys.
- Each build reports how many referenced keys were not found in stock, and how many matched
  only after case folding (section 13, coverage).

There is no key-variant sync. We write a key only when a record references it (by the rule
above), or a patch or override names it.

### 4.4 User overrides file (`overrides.ini`)

```ini
; StarOrg Strings user overrides. One key=value per line.
vehicle_NameAEGS_Avenger_Titan=*05-Avenger Titan
item_NameKLWE_LaserCannon_S3=CF-337 Panther (mine)
```

- UTF-8, no BOM, LF line endings. Lines starting with `;` are comments. Blank lines allowed.
- Split on the first `=`. The value is taken raw: no trimming, no quote handling. A newline in
  a value is the two-character escape `\n`, as in the game file.
- The key is matched against the stock key **without** its flag suffix. Stock has keys such as
  `some_key,P`; the user writes `some_key`. The writer keeps the stock spelling (section 7.2).
- Matching ignores case (section 4.3). A key that is not in stock is ignored with a warning.
  The game file never gains keys.
- An override that breaks a validation rule is skipped with a warning (section 7.3).
- An override replaces the whole value, including anything a generator or patch produced.
- The file is written atomically. The previous version is kept as `overrides.ini.bak`.
- v1 has no favourites feature; a user can still prefix ship names by hand, as in the example.

### 4.5 Patch file format (our own)

A patch describes one CIG data bug and how we correct for it. Files are TOML, named
`<id>.patch.toml`. Built-in patches live in `patches/` and are embedded in the binary. User
patches live in `data/patches/`.

```toml
schema = 1
id = "hockrow-p2m4-desc"
title = "Hockrow facility delve P2M4 shows the P2M1 description"
description = "Contract P2M4 points its Description at the P2M1 key."
reference = "STARC-176797"              # optional Issue Council id or URL

# Optional range. game_* compare the version taken from Data.Branch (section 4.1).
# change_* compare RequestedP4ChangeNum. Empty or 0 = open. Data.Version is never used.
builds = { game_min = "4.10.0", game_max = "", change_min = 0, change_max = 0 }

# Data patch: change a field of one record in GameData before generators run.
[[data]]
id = "p2m4-own-desc"
record = "<generator record name>"      # record short name; or  guid = "..."
contract = "<contract debugName>"       # only for contracts, which sit inside a generator
field = "description_key"
expect = "<P2M1 description key>"       # a loc KEY, never prose
set = "<P2M4 description key>"          # "" means "no loc key" (LOC_EMPTY)

# Loc patch: change an output string after generators run.
[[loc]]
key = "<P2M1 description key>"
op = "append_from"                      # set | append | prepend | replace | append_from
from = "<P2M4 description key>"
from_part = "generated"                 # generated (default) | stock | final
separator = "\\n\\n<EM3>ALSO APPLIES TO: P2M4</EM3>\\n\\n"
requires = "p2m4-own-desc"              # optional link to a data entry in this file
expect_sha256 = ""                      # optional guard on the stock value of `key`
```

The names in angle brackets are confirmed against DataCore in the M2 data mapping and
recorded in the patch files.

**Build range.** HOTFIX and LIVE number `Data.Version` differently (`1.0.191.55227` against
`4.10.200.58746`), so a range on that field would switch every patch off on HOTFIX. Ranges
use the game version from `Branch`, and the change number for exact builds.

**Data patches**

- Select one record by short name (primary) or GUID (for names that are not unique).
- `field` is one of a documented set. v1: `name_key`, `short_name_key`, `desc_key` on items
  and ships; `title_key`, `description_key` on contracts. The schema number lets us add
  numeric stat fields later.
- `expect` and `set` are loc keys. Keys are compared with the folding rule of section 4.3.
- Applied as an overlay on the in-memory `GameData`. Cache files and fixtures are never
  changed. (Smart Citizen edits its extracted cache in place; that caused our earlier false
  "off-by-one" alarm.)

**Loc patches**

- Needed when the game still reads the bugged pointer: a data patch fixes what our generators
  write, a loc patch fixes what the player sees.
- `set` replaces the value with `value`. `append`/`prepend` add `value`. `replace` swaps
  `find` for `value` (plain text, must match exactly once).
- `append_from` appends text taken from another key, after `separator`:
  - `from_part = "generated"`: only what our generators added to that key (the mission body
    without CIG's prose). This is what the Hockrow fix wants. If nothing was generated, the
    entry is `nothing-to-add` and is skipped.
  - `stock`: the other key's stock value. `final`: its value after generators.
- **No ordering, no cycles.** Every loc patch reads its sources from one snapshot taken after
  generators and before any loc patch writes. A patch never sees another patch's result. Two
  enabled patches that write the same key are a `conflict`.
- **Guards never contain CIG's text.** A guard on prose is `expect_sha256` (of the stock
  value). There is no plain-text `expect` on loc entries, so patch files hold no game prose.

**Outcome per entry.** The engine never fails the build because of a patch.

| State | Meaning | Action |
|---|---|---|
| `applies` | The guard matches | Applied |
| `not-needed` | See the table below | Skipped. Shown as "No longer needed: CIG fixed it" |
| `target-changed` | The current value is neither the expected one nor the target | Skipped, warning |
| `nothing-to-add` | `append_from` source part is empty | Skipped |
| `missing` | Record, field or key not found | Skipped, warning |
| `out-of-range` | Build outside `builds` | Skipped |
| `conflict` | Two enabled patches write the same target | Both skipped, warning |

When an entry counts as `not-needed`:

| Entry | Not needed when |
|---|---|
| data | The field already equals `set` |
| loc with `requires` | The data entry it names is `not-needed` (the pointer is fixed, so the text needs no workaround) |
| loc `set` | The stock value already equals `value` |
| loc `replace` | `find` is absent and `value` is present in the stock value |
| loc `append` / `prepend` | The stock value already ends / starts with `value` |
| loc `append_from` without `requires` | Never; it must carry `requires` or `expect_sha256`, or the file is rejected |

A patch whose entries are all `not-needed` is reported as retired. Built-in patches that have
been retired for two consecutive game minor versions are removed from the repo.

### 4.6 Backups

Backups cover **`global.ini` only**. `user.cfg` is never copied back as a whole file; our one
line in it is tracked separately (section 7.4).

A backup is a directory `backups/<YYYYmmdd-HHMMSS>-<reason>/`:

```
manifest.json     { created, reason, app_version,
                    build: { branch, game_version, change, version },
                    file: { existed, on_disk_name, real_path, size, sha256,
                            origin: "ours" | "foreign" | "none", foreign_tool } }
global.ini        copy, if the file existed
```

- `existed: false` is a real state: a clean game has no loose `global.ini`.
- `origin` is `ours` when the hash is in `outputs.json`, otherwise `foreign`. `foreign_tool`
  names the tool when we can tell (section 7.5).
- Reasons:
  - `pre-existing`: the state found before our first apply on this channel. Pinned, never
    rotated out. On our machine this will be Smart Citizen's file for build 4.10.200.58746.
  - `before-apply`, `before-restore`, `manual`.
- **"Original" does not mean this backup.** The game's original state is *no loose file*
  (stock text from `Data.p4k`). The `pre-existing` backup is another tool's file for one
  specific build. Section 7.6 treats the two differently.
- A backup is skipped when the file's hash equals the newest backup's.
- Retention: the pinned one; the newest 10; and the newest backup made under each of the last
  3 game builds, even if older than the newest 10. A hook that applies on every build change
  cannot push out the last backup from before a patch.

### 4.7 Profile (`profile.toml`)

Per channel. Holds: which categories are on, which stat lines are on per category, format
options (stats above or below prose, units), tag builder settings per tag kind, mission
options, the branding stamp switch, and which built-in patches are disabled. Unknown keys are
kept on write so an older app version does not drop newer settings. A profile hash goes into
the applied manifest.

Presets shipped: **Recommended** (all v1 stat blocks, name tags, mission info, patches),
**Minimal** (name tags and patches only), **Everything**.

## 5. Enhancement categories

### 5.1 Rules shared by all categories

**Text conventions (from the stock file and observed in-game rendering)**

- A newline inside a value is the two-character escape `\n`.
- `<EM3>…</EM3>` renders underlined, `<EM4>…</EM4>` renders coloured in mobiGlas. We emit only
  EM3 and EM4. Stock also uses EM1, EM2 and `<EM5>`; we never emit them, and validation treats
  every `<EMn>` the same way.
- There is no glyph for `→`; routes and arrows use `->`. These render and may be used:
  `–` `×` `μ` `°` `’`.
- Stats on one line are joined with two spaces, a pipe, two spaces: `A: 1  |  B: 2`.
- **Percent sign.** A `%` we write is always followed by the end of the value, `\n`, or two
  spaces. It is never followed by a letter or by one space and a letter, because `% c` or
  `%s` would be a format specifier if the game ever formats that string. We also never write
  into keys that contain format specifiers at all (section 7.3).

**Number formats.** Every stat uses one of these classes. Golden tests are written from this
table, not from the examples.

| Class | Rule | Examples |
|---|---|---|
| `int` | Round half away from zero; thousands separators | `1,193` `25` `2` |
| `d1` | At most one decimal; a trailing `.0` is dropped; thousands separators | `225.4` `60` `8` `16.5` `1,700` |
| `d2` | Always two decimals | `0.75` `1.10` `-0.20` |
| `sig2` | Two significant digits, at most four decimals; for values below 0.1 | `0.0054` |
| `pct` | Whole percent, no space before `%` | `25%` `+35%` |

| Stat | Class | Unit text | Zero |
|---|---|---|---|
| HP (shield, armor, component), regen, max distortion | `int` | `HP/s` for regen | left out |
| Speeds (SCM, max, boost, projectile, missile) | `int` | ` m/s` | left out |
| Quantum speed | `int` | ` Mm/s` | left out |
| Angular rates | `int` | `°/s` | left out |
| Fire rate | `int` | ` RPM` | left out |
| Counts (crew, guns, slots, ammo, magazine, pellets) | `int` | | left out |
| Power draw / output, cooling | `int`; a draw below 1 PU/s keeps one decimal (`0.1`), so a real draw never prints as `0` (M2) | ` PU/s`, ` CR/s` | left out |
| EM / IR signature | `int` | | **shown** when the other one is not zero; the line goes when both are |
| Reputation | `int` | | left out |
| Blast radius, falloff start distance | `int` | ` m` | left out |
| Damage (alpha, missile, minimum), DPS | `d1` | | left out |
| Times (delay, spool, cooldown, lock, lifetime) | `d1` | `s`, no space | left out |
| Ranges in km (1,000 m and above), lock range | `d1` | ` km` | left out |
| Ranges below 1,000 m | `int` | ` m` | left out |
| Ship dimensions | `d1` | ` m` after the last one | left out (whole line) |
| Cargo, fuel | `d1` | ` SCU` | left out |
| Mass | `d1` | ` kg` | left out |
| Quantum acceleration, calibration | `int` | | left out |
| Damage multipliers | `d2` | `x`, no space | **shown** |
| Radar sensitivity, falloff per metre | `d2` | | left out |
| Fuel per Gm | `sig2` | ` per Gm` | left out |
| Shield resistance, mining modifiers, blueprint chance | `pct` | | a `0–0%` pair is left out; `0` as the low end of a range is shown |

- A stat whose source value is missing, is zero under "left out", or is a known sentinel is
  **left out**. We never print `?`. A line with no remaining stats is left out. A block with
  no lines is not added at all.
- Sentinels filtered: `jumpRange` above 1e30; container dimension of 900 or more; overheat
  temperature equal to the 450 K placeholder when the item has no heat stats; angular
  velocity read from `speedProfile` (60/200/60 placeholder); `-1` (DataCore's "not set") on
  any magnitude such as a lock range, speed, range, count or HP: a magnitude is printed only
  when it is above zero (`Lock range: -1 m–-1 m` on LIVE's Venom S1 rocket was the case).

**Stat block placement**

- Default: `<stock prose>\n\n--- STATS ---\n<lines>`.
- Option "stats above prose": `--- STATS ---\n<lines>\n\n------\n\n<stock prose>`.
- Trailing `\n` escapes and spaces on the stock value are trimmed before anything is appended.
- The block is always built from the stock value, so nothing ever needs to be stripped from a
  previous run.
- The header text is a profile setting. Item descriptions use plain ASCII headers because
  EM tags are only confirmed to render in mobiGlas text.

**Which record owns a loc key** (namesake rule, applies to name, short-name and description
keys alike)

1. Collect all main records that reference the key (after data patches), after the filters
   below.
2. If one of them is named after the key, it owns the key. "Named after" means the record
   short name equals the key with its `item_Name`/`item_Desc`/`vehicle_Name`/`vehicle_Desc`
   prefix removed, compared case-insensitively and ignoring underscores.
3. Otherwise, if exactly one record references the key, it owns the key.
4. Otherwise, if all referencing records would produce the same text, that text is used.
   (Paint and skin variants usually share every stat, so they land here.)
5. Otherwise the key is left as stock and a diagnostic lists the contenders.

Records filtered out before this rule: non-main records, templates and display props
(placeholder name, or short name ending `_prop`), AI and NPC variants (the player-hull filter
of section 5.2, applied to items mounted only on such hulls), and records whose name resolves
to a placeholder (`@…` unresolved, contains "placeholder", `<= … =>` forms including the
spaced `< = TEST NAME = >`).

M2 applies the AI/NPC filter by record-name token, as a preference rather than a hard
filter: a record named after the key still owns it, and the other records are dropped only
when at least one record without such a token remains. Ship tokens: `AI`, `PU`, `Unmanned`,
`Derelict`, `Template`, `Display`, `ShipBoarded`, `EA`, `Swarm`, `Temp`, `Tutorial`,
`NoInterior`, `Wreck`, `Hijacked`. Item tokens: `template`, `test`, `hologram`,
`FakeHologram`, `balance`, `prop`, `AI`, `NPC`, `display`, `dummy`, `elim`.

Step 5 is the safe choice, but it can quietly leave many keys untouched. Each build therefore
writes a **coverage report** (section 13): per category, how many keys were candidates, how
many were written, and how many were left as stock for each reason. M2 has a ceiling for
"left as stock: contenders differ".

**Name tags**

- Format `<tag> <stock name>` (prefix, default) or `<stock name> <tag>` (suffix), one space.
- Built from DataCore fields, never by parsing description text, with one stated exception
  (component class, section 5.3).
- Tag builder settings per tag kind: which elements, their order, style per element
  (short/medium/long), separator (`-` default; none, space, `_`, `.`, `/`, `|`), enclosing
  (`[]` default; `()`, `{}`, `<>`, none), placement.
- Elements with no value are dropped. If none remain, no tag is added.
- The same tag is written to the item's short-name key when the record references one
  (option; the default is decided by the in-game check in M2, Q10).
- If the stock name is a placeholder, no tag is written.

**Categorisation** is by the component struct an entity carries and by `AttachDef.Type`,
never by port name, and by path only where stated. The order of checks matters and is fixed:
missiles before guns, countermeasures before weapons, quantum fuel tanks before fuel tanks.

### 5.2 Ships

- **Records:** `EntityClassDefinition` under `entities/spaceships/` and
  `entities/groundvehicles/` that carry `VehicleComponentParams`. Player hulls only: AI, PU
  spawn, unmanned, derelict and template variants are skipped when they do not own their loc
  key.
- **Key written:** the ship description (`VehicleComponentParams.vehicleDescription`).
- **Reads:** `vehicleCareer`, `vehicleRole`, `crewSize`, `maxBoundingBoxSize`; the default
  loadout (`SEntityComponentDefaultLoadoutParams`, resolved recursively, items classified by
  their `AttachDef.Type`); the flight controller item's `IFCSParams`; armor item stats;
  cargo grids; fuel tanks.

```
--- STATS ---
Role: Light Fighter  |  Career: Combat  |  Crew: 1
Size: 21 × 16.5 × 5.5 m
SCM: 226 m/s  |  Max: 1,193 m/s
Boost: 520 m/s fwd  |  268 m/s back
Pitch: 71°/s  |  Yaw: 63°/s  |  Roll: 195°/s
Guns: 2× S3, 1× S2  |  Missiles: 4× S3
Shields: 2× S1  |  Power: 1× S1  |  Coolers: 2× S1  |  QD: 1× S1
Armor HP: 3,300
Damage taken: Phys 0.75x  |  Energy 0.60x  |  Dist 1.00x  |  Therm 1.00x
Cargo: 12 SCU  |  H2 fuel: 28 SCU  |  QT fuel: 1.2 SCU
```

Line rules:

| Line | Source and rule |
|---|---|
| Role / Career / Crew | `vehicleRole`, `vehicleCareer` resolved through stock strings; `crewSize` |
| Size | `maxBoundingBoxSize` as length × beam × height = **y × x × z** (M2a: the Gladius is x 17.5, y 21, z 5.5 for a 20 m long, 17 m wide hull) |
| SCM / Max | `IFCSParams.scmSpeed`, `maxSpeed` |
| Boost | `boostSpeedForward`, `boostSpeedBackward` |
| Pitch / Yaw / Roll | `IFCSParams.maxAngularVelocity`: **x = pitch, y = roll, z = yaw**. Never `speedProfile.angularVelocity` |
| Guns | Loadout items of gun type, grouped by size, largest first. A gun under a gun is skipped (stale AI duplicate). Guns on turrets are counted as guns. Only `AttachDef.Type = WeaponGun` counts (tractor beams, mining and salvage heads do not). **No `Turrets` element (M2):** gimbals and turrets share `AttachDef.Type = Turret` and their subtypes overlap (`GunTurret` covers both), so turret mounts cannot be counted reliably |
| Missiles | Missile ports on racks in the default loadout, grouped by size |
| Shields / Power / Coolers / QD | Count and size of each type in the default loadout |
| Armor HP | Health of the armor item in the loadout |
| Damage taken | Armor `damageMultiplier` for physical, energy, distortion, thermal |
| Cargo / fuel | Sum of cargo grid SCU (interior dimensions ÷ 1.953125 per SCU), fuel tank capacities |

Hull HP and ship mass are not in DataCore (they are in the vehicle XML) and are not shown.
Insurance timers are shown as `Insurance: 5.8 min  |  Express: 1.9 min` only if M2a finds the
source field in DataCore; otherwise the line does not exist in v1.

Ships get no name tag in v1.

### 5.3 Ship components

- **Records:** `entities/scitem/ships/`, categorised by the first matching rule:

| Category | Matched by |
|---|---|
| Shield | `SCItemShieldGeneratorParams` |
| Quantum drive | `SCItemQuantumDriveParams` |
| Radar | `SCItemRadarComponentParams` |
| Power plant | `AttachDef.Type = PowerPlant` |
| Cooler | `AttachDef.Type = Cooler` |
| Missile rack / bomb rack | `SCItemMissileRackParams` |

  Other categories (thrusters, tanks, armor, life support, jump drives, EMP, QED) get the
  common lines only in v1, and only if at least two common lines have data.
- **Keys written:** description (stat block), name and short name (tag).
- **Common reads:** power draw (`ItemResourceComponentParams`, the `Online` state,
  consumption of Power), EM and IR (`signatureParams` nominal signatures), component health
  (`SHealthComponentParams.Health`), max distortion (`SDistortionParams.Maximum`).

Common lines, appended after the category lines:

```
Power draw: 2 PU/s
Signatures: EM 500  |  IR 0
Component HP: 300  |  Max distortion: 2,450
```

Shield:

```
--- STATS ---
Shield HP: 7,480  |  Regen: 1,346 HP/s
Delay: 8.5s when down  |  4.2s when damaged
Resist: Phys 0–25%  |  Energy 0–10%  |  Dist 0–90%
```

Reads `MaxShieldHealth`, `MaxShieldRegen`, `DownedRegenDelay`, `DamagedRegenDelay`,
`ShieldResistance` (positional min/max by damage type, order physical, energy, distortion,
thermal, biochemical, stun). Resist entries that are 0–0 are left out.

Quantum drive:

```
--- STATS ---
Speed: 301 Mm/s  |  Spool: 8s  |  Cooldown: 16.5s
Fuel: 0.0054 per Gm
Accel: stage 1 6,936,600  |  stage 2 10,494,000
Calibration: 1,000/s  |  Needs 5,000–10,000
```

Reads `params.driveSpeed` (÷ 1e6), `spoolUpTime`, `cooldownTime`, `quantumFuelRequirement`,
`stageOneAccelRate`, `stageTwoAccelRate`, `calibrationRate`, `min/maxCalibrationRequirement`.

Power plant: `Output: 20 PU/s` (Online state generation of Power).

Cooler: `Cooling: 46 CR/s` (Online state generation of Coolant).

Radar:

```
--- STATS ---
Ping cooldown: 2.5s
Detects: IR 1.10  |  EM 1.10  |  CS 1.00
```

Reads `pingProperties.cooldownTime` and `signatureDetection[].sensitivity`. **The detection
line is dropped in v1 (M2):** `signatureDetection[]` has eight positional entries and no field
names the signature type, so they cannot be labelled reliably.

Missile rack and bomb rack: `Slots: 4× S3` (count and maximum size of ports whose type is
Missile). No separate Size or Grade line; those are in the tag.

**Component name tag.** Default `[MIL-S1-B]`: class (medium style), size (`S<n>`), grade
(letter).

- Size and grade: `AttachDef.Size`, `AttachDef.Grade` (grade number mapped to letter A–D).
- Class: Military `MIL`, Civilian `CIV`, Industrial `IND`, Stealth `STH`, Competition `CMP`.
  M2a looks for a DataCore field first. If there is none, class is read from the owning
  record's own English stock description with one anchored pattern (a line starting
  `Class:`). This is the only place we read a value out of description text. When no class is
  found the element is dropped, giving `[S1-B]`.
- Tagged categories: shields, power plants, coolers, quantum drives, radars. Racks get
  `[S3]`.

### 5.4 Ship weapons

- **Records:** `entities/scitem/ships/weapons/` with `SCItemWeaponComponentParams`. Records
  with `SCItemMissileParams` are missiles (section 5.6). Countermeasure launchers
  (`AttachDef.Type = WeaponDefensive`) are excluded.
- **Reads:** fire actions; ammo through `SAmmoContainerComponentParams.ammoParamsRecord`;
  capacitor (`weaponRegenConsumerParams`: cost per shot, `requestedRegenPerSec` for Regen,
  which is in the cost unit; `maxRegenPerSec` counts shots and is not shown); heat
  (`simplifiedHeatParams`); common block.

```
--- STATS ---
Damage: 225.4 Phys  |  DPS: 375.7
Fire rate: 100 RPM  |  Mode: Semi
Velocity: 1,184 m/s  |  Range: 3 km
Ammo: 387
Capacitor: 90 per shot  |  Regen: 1,125/s after 1.4s
Power draw: 2 PU/s
Signatures: EM 41  |  IR 0
Component HP: 550
```

Calculation rules:

- **Ammo damage** = the first `DamageInfo` with any non-zero component in the ammo's
  projectile params. The damage type shown is the largest component. Mixed damage prints the
  two largest: `120 Phys + 30 Energy`.
- **Alpha** = ammo damage total × pellet count (default 1) × damage multiplier (default 1).
  Multi-pellet weapons print `Damage: 49.5 ×8 Energy`.
- **Fire rate by action type:**

| Action | Rate | Mode label |
|---|---|---|
| `SWeaponActionFireSingleParams` | `fireRate` | `Semi` |
| `SWeaponActionFireRapidParams` | `fireRate` | `Auto` |
| `SWeaponActionFireBurstParams` | sustained: `60·n / (n·60/fireRate + cooldown)` | `Burst n` |
| `SWeaponActionFireChargedParams` | from the nested action | `Charged` |
| `SWeaponActionSequenceParams` | from the sequence entries: `60·Σrep / Σ(perShot·rep)`, where `perShot` is `delay` in seconds or `60/delay` | label of the nested action |
| `SWeaponActionFireBeamParams` | none; DPS = sum of `damagePerSecond` | `Beam` |

- **DPS** = alpha × rate ÷ 60. The headline mode is the one with the highest DPS. If a weapon
  has more than one distinct mode, the Mode value lists them: `Mode: Auto / Burst 3`.
- **Range** = ammo `speed × lifetime`, shown in km above 1,000 m. Beams use
  `zeroDamageRange`.
- **Ammo** = magazine `maxAmmoCount`. For capacitor weapons the Ammo line is replaced by the
  Capacitor line.
- Weapons with no damage-dealing mode (tractor beams, salvage heads, mining lasers) get no
  Damage, Fire rate, Velocity or Ammo lines. Mining lasers get the modifier line below;
  tractor and salvage items get the common lines only.
- Sustained DPS and overheat times are not shown in v1 (they rest on an assumption about
  cooling while firing).

Mining laser:

```
--- STATS ---
Modifiers: Instability +35%  |  Resistance +25%  |  Optimal window +40%
```

Reads `MiningLaserModifier` values (each wrapped in a multiplicative or additive modifier
struct; note the data spells `shatterdamageModifier` with a lowercase d).

**Ship weapon name tag.** Default `[E-S2]`: damage type (short: `P` physical, `E` energy,
`D` distortion, `T` thermal, `B` biochemical, `S` stun) and size from `AttachDef.Size`. No
damage-dealing mode means no damage element; rocket pods therefore get `[S1]`, and tractor
beams and EMPs get a size-only tag or none (profile switch, default none).

### 5.5 FPS weapons

- **Records:** `entities/scitem/weapons/` with `SCItemWeaponComponentParams`.
- **Reads:** same fire-action rules as ship weapons. Ammo comes through the default loadout:
  the entry whose port name contains `magazine` → that magazine entity →
  `SAmmoContainerComponentParams`. Falloff from the ammo's `damageDropParams`. Mass from
  `SEntityPhysicsControllerParams.PhysType.Mass`.

```
--- STATS ---
Damage: 60 Phys  |  DPS: 180
Fire rate: 180 RPM  |  Mode: Semi
Velocity: 550 m/s  |  Range: 1.1 km
Full damage to 55 m  |  then -0.20 per m  |  Min: 35
Magazine: 6  |  Weight: 1.3 kg
```

- The falloff line uses `damageDropMinDistance`, `damageDropPerMeter`, `damageDropMinDamage`
  for the dominant damage type, and is left out when the per-metre drop is zero.
- A rifle with 300 and 900 RPM modes prints `Fire rate: 900 RPM  |  Mode: Auto / Burst 3`
  (headline = highest DPS mode).
- Tools (multi-tool heads, medical, repair, salvage) get no block in v1.
- FPS weapons and armor get no name tag in v1.

### 5.6 Missiles and bombs

- **Records:** ship-item records with `SCItemMissileParams`. A bomb is a record whose
  `AttachDef.Type` is `Bomb` or that carries `SCItemBombParams`.
- **Reads:** `explosionParams.damage`, `explosionParams.maxRadius`, `targetingParams`
  (`trackingSignalType`, `lockTime`, `lockRangeMin`, `lockRangeMax`), `GCSParams.linearSpeed`,
  `maxLifetime`, health.

```
--- STATS ---
Damage: 1,700 Phys  |  Blast radius: 3 m
Tracking: Infrared  |  Lock: 1.5s
Lock range: 1.8–10 km
Speed: 1,250 m/s  |  Lifetime: 30s
Component HP: 25
```

- Mixed damage prints the components: `Damage: 27,000 (12,500 Phys + 14,500 Energy)`.
- Bombs have no Tracking, Lock or Lock range lines.

**Name tag.** Default `[IR-S2]`: tracking signal (Infrared `IR`, Electromagnetic `EM`,
CrossSection `CS`) and size. Bombs: `[B-S3]`. A missile whose name key is not in stock gets
no entry at all; we never invent a name.

### 5.7 Branding stamp (off by default)

Option "Show StarOrg Strings in the game's version text". When on, `Frontend_PU_Version` gets
`\nText enhanced with StarOrg Strings v<version>` appended, unless that key turns out to be a
format key (section 7.3). Detection of our own output does not depend on this stamp
(section 7.5).

## 6. Mission and blueprint logic

### 6.1 Sources

- **Contracts:** contract generator records (`contracts/contractgenerator/`,
  `contractscenarios/`): `generators[] → contracts[]`, each with `debugName`,
  `paramOverrides.stringParamOverrides[]` and `contractResults`.
- **Title and description keys:** the `Title` and `Description` string param overrides of the
  contract, else of its generator handler (`contractParams`), else the contract template's
  `contractDisplayInfo.displayString` (`[0]` title, `[2]` description; confirmed in M2a on
  LIVE 4.10: 2,506 contract, 24-27 generator, 21-24 template, 2 none). The adapter records
  which path supplied each key (`KeySource`).
- **Blueprint rewards:** `BlueprintRewards { blueprintPool, chance }` nodes inside
  `contractResults`.
- **Pools:** `BlueprintPoolRecord.blueprintRewards[] { blueprintRecord, weight }`.
- **Blueprint names:** `CraftingBlueprintRecord` → produced item
  (`processSpecificData.entityClass`) → that item's name. The record's own `blueprintName` is
  a placeholder on almost every record and is not used. Dismantle records (no tiers) are
  skipped.
- **Item rewards:** `ItemAwardEntityClass { entityClass, amountToAward }` inside
  `contractResults`.
- **Reputation:** the first positive reputation reward in `contractResults`, resolved through
  the reputation reward records; the required standing through `SReputationStandingParams`
  (`displayName`, `minReputation`).
- **Legacy missions** (`MissionBrokerEntry`) are not annotated in v1.

### 6.2 Grouping

Many contracts share one title key or one description key (difficulty variants). The
generator builds two maps: title key → contracts, description key → contracts. All output for
a key is computed from **all** contracts in its group, never from the first one.

Hard rules:

- A key that is used as a title by any contract never receives a description body.
- A key equal to `LOC_EMPTY` or missing from stock is skipped.
- A format key (its stock value has `%s`-style specifiers) is skipped (section 7.3).
- Trailing `\n` escapes and spaces are trimmed from a title before tags are appended.

### 6.3 Title tags

Appended to the title in this order, each as ` <EM4>[…]</EM4>`:

| Tag | Condition (over the title's contract group) |
|---|---|
| `[BP]` | Every contract awards a blueprint pool with chance 1.0 |
| `[BP?]` | At least one contract awards a pool, and the `[BP]` condition is not met |
| `[N Rep]` | All contracts give the same reputation amount N |
| `[A–B Rep]` | Reputation amounts differ; A is the lowest, B the highest |

Each tag has its own switch. EM tags are confirmed to render in mobiGlas only; titles also
appear in the HUD mission tracker and in notifications. The M2 in-game check decides whether
title tags keep `<EM4>` or fall back to plain `[BP]` (section 13). Example:

`Operative Extraction <EM4>[BP]</EM4> <EM4>[150 Rep]</EM4>`

`[BP?]` means "this title can award a blueprint, depending on the variant or on chance". The
description body says which. Static text cannot say "only if you do not own it yet"; the help
text states this.

### 6.4 Description body

Sections are joined with `\n\n`, in this order. A section with no content is left out.

```
<stock prose>

<EM3>BLUEPRINTS</EM3>
- Item Name A
- Item Name B

<EM3>ITEM REWARDS</EM3>
- MG Scrip ×3

<EM3>MISSION DETAILS</EM3>
<EM4>Blueprint reward:</EM4> Guaranteed
<EM4>Reputation:</EM4> 150
<EM4>Requires:</EM4> Jr. Contractor
<EM4>Type:</EM4> Chain, Once only
```

- **BLUEPRINTS.** Display names of the craftable items in the pools of the description's
  contract group, de-duplicated, sorted by bare name (case-insensitive, tags ignored). When
  the group has more than one distinct pool, each pool gets a sub-header
  `<EM4>[<variant label>]</EM4>`, where the label is the contract's difficulty or tier taken
  from data, falling back to `Variant n`. (M2: pools are compared by their bullet lists, so two
  pool records with the same items count as one. The label is the difficulty profile name,
  title-cased, when every pool's contracts share one and the labels differ between pools;
  otherwise `Variant n`.) Lists longer than 25 entries are cut with
  `- and N more`. Bullets carry the item's name tag when the option is on (default on).
- **ITEM REWARDS.** Union over the whole contract group, with amounts when above 1 (a range
  `×A–B` when the variants award different amounts).
- **Blueprint reward.** `Guaranteed` when all chances are 1.0; `N%` when all are equal and
  below 1.0; `N–M%` when they differ; `Some variants only` when part of the group has no
  pool. The percent sign always ends the line (section 5.1).
- Stock contract descriptions are where CIG's unbalanced EM tags live. The body is appended
  under the rules of section 7.3; a description that would break them keeps its stock text.
- **Reputation.** One value or a range, same rule as the title tag. A failure penalty adds
  `<EM4>Failure:</EM4> -1,000`.
- **Requires.** The lowest required standing's display name, when present.
- **Type.** `Chain` (the contract has linked or prerequisite contracts), `Once only`
  (`onceOnly`), each when every contract of the group has it. Left out when neither applies.
- Contracts flagged `notForRelease` or `workInProgress` are not used.
- Section header text and the emphasis tag (EM3 or EM4) are profile settings.

Hauling routes, spawn counts, difficulty breakdown, ace-pilot detection and engagement type
are out of v1 (open question Q6).

### 6.5 Owned blueprints

The addendum asks for a post-exit hook that reads `Game.log` for "Received Blueprint"
notifications and marks bullets `[Owned]`. The blueprints section keeps bullets as structured
data until render time. The generator asks one trait, `enhance::owned::OwnedBlueprints`
(`owns(id, record, display name)`), so M1's per-character store plugs in without the
generator knowing where the set came from (M2). A marked bullet reads
`- <tag> <Item Name> [Owned]`. `build --owned-blueprints FILE` reads an owned-set JSON (M1's
`{"entries": {...}}` shape) or a JSON list of names; names are matched after stripping
leading `[...]` tag groups and folding quotes, whitespace and case.

## 7. Apply, backup, rollback, validation

### 7.1 Apply sequence

1. **Lock.** Take an OS advisory lock (`flock` on Linux, `LockFileEx` on Windows) on
   `locks/<install-id>-<CHANNEL>.lock`. The lock is held by the open file handle and the
   system releases it when the process dies, so a leftover file never blocks anything. A held
   lock means exit code 3 (CLI) or a disabled button with the reason (GUI).
2. **Recover.** If `intent.json` exists, a previous apply was interrupted. Finish or undo it
   (see "Journal" below) before going on.
3. **Guards.** Refuse when:
   - the channel is not set up (exit 6);
   - the channel's game language is not English and no switch was agreed (exit 6,
     section 7.4);
   - the process is elevated or root;
   - `StarCitizen.exe` is running for this channel (section 10.6);
   - `Data.p4k` is being written: size or mtime changes between two reads 500 ms apart, or the
     launcher log shows an install pipeline in progress for this channel.
   A running RSI Launcher alone is a warning, not a refusal.
4. **Load.** Use the cache entry when it exists and its hashes check out; otherwise extract in
   the worker process (section 3.3).
5. **Build.** Data patches → generators → merge → loc patches → overrides.
6. **Validate** (section 7.3). Edits that fail a per-value rule are dropped one by one. Then
   the rendered file is checked as a whole. A whole-file failure stops here with nothing
   changed on disk.
7. **Preflight.** Resolve the real paths of both targets (case, symlinks). Do a write probe
   (create and delete a temp file) in the folder that will hold `global.ini`. Work out
   whether `user.cfg` needs a change at all. Any failure stops here with nothing changed.
8. **Back up** the current `global.ini` (section 4.6).
9. **`user.cfg`**, only if a change is needed (section 7.4). It is done **before**
   `global.ini`: if it cannot be written, the string table has not been touched yet.
10. **Journal.** Write `intent.json`: output SHA-256, real target path, temp file name,
    backup id, whether step 9 changed anything.
11. **Write** `global.ini`: temp file `global.ini.starorg-tmp` in the same folder, fsync,
    rename over the target, fsync the folder (Linux).
12. **Verify** by reading the file back and comparing its SHA-256 with the rendered bytes. On
    mismatch: put back the state from step 8 (copy the backup, or delete ours when no file
    existed), undo step 9, report failure.
13. **Record** `applied.json` and add the hash to `outputs.json`. Delete `intent.json`.
14. **Report** counts per category, coverage, patch outcomes, warnings, backup id.

Because validation and preflight happen before anything is written, a normal failure leaves
the game directory untouched. Step 12 covers I/O faults only.

**Journal.** `intent.json` closes the gap between writing the file and recording it. On the
next run of any command for that channel:

| Found | Meaning | Action |
|---|---|---|
| Game file hash equals the intent's output hash | The write finished, the record did not | Write `applied.json` and `outputs.json`, delete the intent |
| Temp file exists, game file unchanged | Killed before the rename | Delete the temp file, undo the `user.cfg` change if the intent says one was made, delete the intent |
| Neither | Killed before writing | Same undo, delete the intent |

Without this, our own output would later look like another tool's file.

**Time budget and signals.** `--timeout` and SIGTERM/Ctrl+C are honoured between steps and
during step 4 (the worker is killed, its partial cache folder removed). Steps 9 to 13 are
short and are never interrupted part-way.

### 7.2 Writer rules

- Output is the stock file streamed line by line.
- A line that is not changed is copied **byte for byte**: key spelling including any flag
  suffix such as `,P`, spacing, comments, blank lines and its own line ending. Every
  flag-suffixed key in stock survives (13,612 of them on LIVE 4.10.200.58746; the count
  differs per build).
- For a changed line, only the bytes after the first `=` and before the line ending are
  replaced.
- The UTF-8 BOM at the start of the stock file is kept. Without it the game shows every
  string as `@key`. The whole-file rule checks the output for the BOM whatever the stock
  input looked like: a stock without one means the input is wrong, and nothing is written.
- Line endings are kept per line as found in stock (CRLF).
- No key is added, removed or reordered.

### 7.3 Validation

Validation compares our output with **stock**, not with an ideal. Stock is not clean: about
19 contract descriptions on LIVE 4.10 have unbalanced EM tags (for example
`Battaglia_RPT_ScanMine_05_desc`, `Covalex_internaldelivery_dc_desc_001`,
`Intersec_TSG_Assist_Solo_Desc_001`), 5 have nested ones, and 2,052 values contain `%`. A rule
that demanded clean values would block every apply.

**Tokens** (definitions used below)

| Token | Pattern | Examples |
|---|---|---|
| Variable | `~` + letters + `(` … `)` | `~mission(Location|Address)`, `~action(...)` |
| Format specifier | `%` + optional flags (`-+ 0#`) + optional width + optional `.precision` + optional `l`/`ll`/`h` + one of `s S d i u f F g G x X c` | `%s` `%ls` `%S` `%i` `%d` `%u` `%.2f` `%02i` |
| Escaped percent | `%%` | |
| Literal percent | any other `%` | `25%` |
| EM tag | `<EMn>` / `</EMn>`, any digit | |

A **format key** is a stock key whose value contains at least one format specifier.

**Per-value rules.** They run on every changed value. A value that fails is **dropped**, the
next lower layer is tried (override → loc patch → generated → stock), and a warning names the
key and the rule. Stock always passes. A dropped edit never stops the apply.

| Rule | Applies to |
|---|---|
| No raw CR or LF, no control characters other than tab | all |
| Text we add (a prefix or suffix part) has balanced EM tags, none nested | generated, `append`, `prepend`, `append_from` |
| The EM signature of the whole value (per tag number: unmatched opens, unmatched closes, nested count) equals the stock value's signature. A whole-value replacement may instead be fully balanced, so a user can repair CIG's tags | all |
| Stock's variable tokens are all still present, in order. Added text may bring variable tokens only when it was taken from another stock value (`append_from` with `stock`/`final`); such tokens are in addition | all |
| The sequence of format specifiers equals stock's exactly: same specifiers, same order, none added, none removed | all |
| Format keys get no generated text and no `append`/`prepend`/`append_from`. Only `set`, `replace` and overrides may change them, and the result must contain no literal `%` | all |
| A `%` we add follows the percent rule of section 5.1 | generated |
| Value is at most 64 KiB | all |

If a stock value ends inside an open EM tag, text appended to it would take on that styling.
We still append; the coverage report counts these keys as `open-tail`; the M2 in-game check
looks at two of them and decides whether such keys are skipped instead.

Keys such as `text_ui_tags_EM4_open` hold a lone opening tag on purpose. No generator owns
them, and an override on them must keep the stock signature.

**Whole-file rules.** They run on the rendered bytes. Any failure stops the apply before
anything is written; it means a bug in our writer.

| Check | Failure means |
|---|---|
| First three bytes are `EF BB BF` | Game would show raw keys |
| Valid UTF-8 | Corrupt output |
| Same number of lines, same line endings | A value split a line, or a writer bug |
| Same key sequence, byte-identical key text | A key was dropped, added or renamed |

**Warnings** (do not block; they make the result "applied with warnings", exit 5): dropped
edits; a patch in `target-changed` or `missing`; schema drift; a changed value longer than
16,000 bytes (stock itself ships one of 16,026 bytes, so the game accepts at least that; the
real limit is unknown, Q9).

### 7.4 `user.cfg`

The game reads the loose `english/global.ini` when its language is English. We own exactly
one line in `user.cfg`: `g_language = english`. Everything else in that file is the user's.

**Finding the file.** Case-insensitively in the channel directory (`USER.cfg` here). On our
machine `LIVE/USER.cfg` and `HOTFIX/USER.cfg` are both **symlinks** to
`/mnt/games/star-citizen/shared/USER.cfg`, one file shared by two channels; PTU has none.

**Symlink policy** (same for `global.ini` and the folders above it):

- Links are followed to the real file. We edit the real file in place (temp file beside the
  **real** target, rename over the real target). A link is never replaced by a regular file.
- The real target must be a regular file owned by the current user. Otherwise: refuse, with
  the path in the message.
- The report and the review dialog say when a target is a link and which channels share it.
- A second advisory lock, keyed by the real path (`locks/cfg-<hash>.lock`), covers a file
  shared by several channels. Apply waits for it (up to 10 s) and then **reads and plans the
  file again under the lock**: another channel's run may have changed it since the first
  read, and text computed from that read must never be written.

**Deciding what to do.** Match `^\s*g_language\s*=` case-insensitively; the value may be
quoted and may be followed by a `;` or `#` comment.

| Found | Action |
|---|---|
| Line present, value `english` | **Nothing is written.** (This is our machine today.) |
| Line missing, or no `user.cfg` | Append `g_language = english` (create `user.cfg` if needed). Whether the line is needed at all when it is missing is tested in M1; if not, this row becomes "nothing" |
| Line present, another language | **Stop.** v1 writes English only, and replacing the line would switch the user's game to English. The wizard explains this and asks. `starorg-strings setup --switch-language` is the CLI form. Without that recorded decision, apply exits 6. A hook never switches language on its own |

Every other line, every comment and the file's line endings are kept.

**Ledger.** For each real `user.cfg` we changed, `data/cfg/<hash>.json` records: the real
path; what was there before (`absent`, or the exact previous line); the line we wrote; the
list of channels that rely on it; and a reference copy of the file from before our first
change (for the user to look at; the app never copies it back).

**Undoing it** (on remove, section 7.6): the channel is taken off the ledger's list. When the
list is empty, and only if the current line is still byte-for-byte the one we wrote, the line
is removed (`absent`) or the previous line is put back. If someone changed the line since, it
is left alone and the report says so. Removing LIVE while HOTFIX is still applied therefore
leaves a shared file untouched.

### 7.5 Applied manifest and status

`applied.json` records: branch, game version, change number, data fingerprint, cache key,
profile hash, patch-set hash, overrides hash, app version, SHA-256 of the output, time,
backup id, warnings.

| Status | Condition |
|---|---|
| **Applied** | Game file hash equals the recorded output hash, and all recorded inputs equal the current ones |
| **Stale** | Game file is ours (hash in `applied.json` or `outputs.json`), but the build, profile, patches, overrides or app version changed |
| **Changed by another tool** | A loose `global.ini` exists whose hash is not in `outputs.json` |
| **Not applied** | No loose `global.ini` |

Status needs no extraction: it hashes one 11 MB file and reads `build_manifest.id`. This is
what makes a no-op launch-hook run fast.

"Changed by another tool" also names the tool when it can: a `Frontend_PU_Version` value
containing "Smart Citizen", or a `.starstrings_version` file in the channel directory. Apply
is still allowed in the GUI and with `setup` consent (the `pre-existing` backup keeps the
foreign file), with a warning not to run two tools on one channel.

### 7.6 Remove and restore

There are three different actions. All run under the same locks and guards as apply.

**1. Remove StarOrg changes (back to stock).** This is the default "undo everything", in the
GUI, in `starorg-strings remove` and in the Windows uninstaller.

- Delete the loose `global.ini`. The game then reads the stock table from `Data.p4k`, which
  always matches the installed build. When `global.ini` is a link, the file it points to is
  deleted and the link is kept (a link is never replaced, 7.4); the report says so
  (`link-kept`), and the next apply writes through the dangling link again.
- Undo our `user.cfg` line by the ledger rule (section 7.4). No other line is touched.
- Delete `applied.json`. Backups, profile and overrides stay.
- If the loose file is not ours (hash not in `outputs.json`), it is backed up first and the
  dialog says a file from another tool will be removed.

**2. Undo the last apply.** Restores the newest `before-apply` backup of our own output. Only
offered when that backup was made under the current change number; otherwise the offer is
"Re-apply" instead, because the file is regenerable.

**3. Restore the file from before StarOrg Strings.** Puts the pinned `pre-existing` backup
back. This is another tool's string table for one build, so:

- It is only offered when that backup's `origin` is `foreign`.
- If the backup's change number equals the current one, it restores after one confirmation.
- If the game has been patched since, the dialog says the file was made for build X, the game
  is now build Y, and new text would show as raw `@keys`. It needs a second, explicit
  confirmation. The CLI needs `--allow-build-mismatch`. A hook can never do this.

`user.cfg` is never restored from a copy by any of these actions.

## 8. CLI contract

Binary: `starorg-strings` on both systems (section 2). It never opens a window, needs no
display, and does not link GTK or WebView2.

```
starorg-strings setup    --channel <NAME> (--preset recommended|minimal|everything | --copy-from <CH>)
                         [--switch-language] --yes
starorg-strings apply    (--channel <NAME> | --all) [--if-stale] [--dry-run] [--profile <file>]
                         [--timeout <seconds>]
starorg-strings status   [--channel <NAME>]
starorg-strings remove   (--channel <NAME> | --all) [--yes]              # back to stock (7.6)
starorg-strings restore  --channel <NAME> --backup <id> [--allow-build-mismatch]
starorg-strings backups  --channel <NAME>
starorg-strings build    --channel <NAME> --out <file>     # write output to a file, touch nothing else
starorg-strings channels
starorg-strings patches  [--channel <NAME>]
starorg-strings doctor
starorg-strings gui                                        # start the app, if installed
```

Global options:

| Option | Meaning |
|---|---|
| `--game-dir <path>` | Install root (the folder that contains `LIVE`). Skips discovery |
| `--prefix <path>` | Linux: Wine prefix to look in. Defaults to `$WINEPREFIX` when set |
| `--json` | One JSON object on stdout; logs go to stderr |
| `--quiet` | Errors only |
| `--notify` | Linux: desktop notification with the result (see below). Ignored on Windows in v1 |
| `--no-cache` | Force a fresh extraction |

**Set-up and consent.** `apply` only works on a channel that is set up. Setting up is an
explicit act (the wizard, or `setup ... --yes`) because the first apply on a channel may back
up and replace another tool's file and may add a line to `user.cfg`.

- `apply --channel X` on a channel that is not set up: exit 6, with the `setup` command to
  run in the message.
- `apply --all` applies every set-up channel of the install and skips the others (listed in
  the report). A new channel such as PTU appearing later is never touched by a hook until the
  user sets it up.
- `setup --copy-from LIVE` copies LIVE's profile; `--preset` starts from a preset.

`apply` behaviour:

- `--if-stale`: do nothing when the status is Applied.
- `--dry-run`: run everything up to and including validation and preflight; write nothing;
  print the report.
- `--timeout <seconds>`: give up when the budget runs out before the write phase
  (section 7.1). Exit 3, nothing changed. No default; the hook passes one.
- Without `--channel` or `--all`, the default channel from config is used; with no config,
  exit 2.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | Applied, or already up to date, no warnings |
| 1 | Error (extraction, whole-file validation, I/O; any partial change was undone) |
| 2 | Usage error |
| 3 | Skipped, try again later: game running, `Data.p4k` being written, lock held, or timeout |
| 4 | No install or channel found |
| 5 | Applied, **with warnings**: schema drift, dropped edits, patches that no longer match. The text may be missing whole stat categories |
| 6 | Needs a decision from the user: channel not set up, game language is not English, or a restore across builds |

With `--all`, the exit code is the most serious one over all channels (1, then 6, 4, 3, 5, 0)
and the JSON has one entry per channel.

`--json` shape for `apply` (fields are only ever added within a major version):

```json
{
  "schema": 1,
  "channels": [ {
    "channel": "LIVE",
    "result": "applied",          // applied | up-to-date | skipped | failed | dry-run | needs-setup
    "reason": null,
    "build": { "branch": "sc-alpha-4.10.0", "game_version": "4.10.0",
               "change": 13165946, "version": "4.10.200.58746" },
    "counts": { "changed": 9412, "ships": 231, "components": 1840, "ship_weapons": 402,
                "fps_weapons": 318, "missiles": 96, "missions": 2140, "overrides": 3,
                "dropped": 0 },
    "patches": [ { "id": "hockrow-p2m4-desc", "state": "applies" } ],
    "warnings": [ { "kind": "schema-drift", "detail": "radar detection line dropped" } ],
    "user_cfg": { "changed": false, "link_target": "/mnt/games/star-citizen/shared/USER.cfg" },
    "backup": "20261114-213005-before-apply",
    "duration_ms": 1830
  } ]
}
```

**`--notify`.** The CLI has no GTK. It runs `notify-send` when that program is on `PATH`, and
otherwise only logs. No D-Bus library is linked. A notification is sent for exit codes 1, 5
and 6, and for 0 only when something was actually applied.

**Launch hooks.** On our machine the Smart Citizen block in `sc-prelaunch.sh` is replaced by
the snippet below, and the same snippet is added to `sc-postexit.sh`. Pre-launch runs after
`wineserver -k` with `WINEPREFIX` exported, so the game is not running.

```bash
if command -v starorg-strings >/dev/null 2>&1; then
    starorg-strings apply --all --prefix "$WINEPREFIX" --if-stale --timeout 60 --notify
    case $? in
        0|5) ;;                                   # applied or up to date (5: warnings, notified)
        3)   echo "starorg-strings: skipped (busy or out of time)" ;;
        *)   echo "starorg-strings: apply failed (non-fatal)" ;;
    esac
fi
```

- **Known gap.** The launcher downloads a game patch *after* the pre-launch hook has run. The
  first session after a patch then has our string table from the previous build. How bad that
  is depends on whether a loose `global.ini` fully replaces the table in `Data.p4k` (new keys
  would show as raw `@key`) or is laid over it. M1 tests this in game. The post-exit run
  fixes it for the next session. A watcher that applies when the launcher finishes patching
  is a later feature (Q5).

## 10. Platform

### 10.1 Install discovery

Order, first valid result wins for the default; all results are listed in the wizard.

**Both systems**

1. `--game-dir` or the saved config.

**Windows**

2. RSI Launcher logs, `%APPDATA%\rsilauncher\logs\log.log` and `log.old.log`, newest first,
   reading at most the last 4 MiB of each. Lines of interest:
   - `[Launcher::launch] Launching Star Citizen <CH> from (<path>)`: the channel actually
     played.
   - `[Pipeline] Installing Star Citizen <CH> <ver> at <library root>`.
   Paths are JSON-escaped and are unescaped before use.
3. Common paths on every drive: `Program Files\Roberts Space Industries\StarCitizen`,
   `Roberts Space Industries\StarCitizen`, `Games\Roberts Space Industries\StarCitizen`, and
   one level of `<drive>\<folder>\StarCitizen`.
4. A deep scan only when the user asks; depth-limited and cancellable.

**Linux**

2. `--prefix` or `$WINEPREFIX`.
3. LUG Helper config: `${XDG_CONFIG_HOME:-~/.config}/starcitizen-lug/winedir.conf` and
   `gamedir.conf`, when present.
4. `~/Games/star-citizen` and `~/games/star-citizen`.
5. Lutris game files (`~/.local/share/lutris/games/*.yml`, `~/.config/lutris/games/*.yml`),
   entries whose slug contains `star-citizen`. Best effort; verified in M3.
6. For each prefix (a directory with `drive_c/` and `system.reg`): the default path
   `drive_c/Program Files/Roberts Space Industries/StarCitizen`, plus the launcher logs under
   `drive_c/users/*/AppData/Roaming/rsilauncher/logs/` (skip `Public`). Windows paths from
   the log are mapped: `C:` → `<prefix>/drive_c`, `Z:` → `/`, other letters through
   `<prefix>/dosdevices/<x>:`.
7. A scan of `/mnt`, `/run/media/$USER` and `$HOME` only when the user asks.

Rules for both:

- A channel is valid when its directory contains `Data.p4k`.
- All paths are canonicalised (realpath) before comparing. `~/games/star-citizen` and
  `/mnt/games/star-citizen` are the same prefix on our machine and must appear once.
- The launcher's `store.json` is encrypted and is not read.
- Log formats are undocumented. Parsing is defensive; a parse failure falls through to path
  scanning.
- StarBreaker's own discovery is not used (it skips HOTFIX and prints to stderr).

### 10.2 Paths per system

| | Windows | Linux |
|---|---|---|
| Game file | `<root>\<CH>\data\Localization\english\global.ini` | `<prefix>/drive_c/…/StarCitizen/<CH>/Data/Localization/english/global.ini` (casing as found) |
| User config | `<root>\<CH>\user.cfg` | `<…>/<CH>/USER.cfg` (casing as found; may be a symlink, section 7.4) |
| CLI binary | `starorg-strings.exe` in the install folder, optionally on `PATH` | `/usr/bin/starorg-strings`, or `~/.local/bin/starorg-strings` for AppImage and tarball installs |
| GUI binary | `StarOrg Strings.exe` | `/usr/bin/starorg-strings-app`, or the AppImage |

### 10.3 Case-insensitive path resolution

On Linux the prefix is a case-sensitive filesystem that Wine reads case-insensitively. Our
machine has `Data/` and `USER.cfg`. Writing `data/` or `user.cfg` would create a second entry,
and which one Wine uses is undefined.

`resolve_ci(base, components)`:

- For each component, list the directory and pick the entry that matches case-insensitively.
- If two entries match (a duplicate already exists), stop with an error that names both.
  `doctor` reports this too.
- If none matches, the component is created with the spelling the game uses on Windows
  (`Data`, `Localization`, `english`, `global.ini`, `user.cfg`).

The same function is used on Windows, where it reduces to the plain path.

### 10.4 Linux WebKitGTK on NVIDIA and Wayland

Before `tauri::Builder` and before any thread starts, the GUI's `main()` sets rendering
workarounds unless the user already set any of these variables:

- NVIDIA GPU with a Wayland session that uses explicit sync (KDE): `__NV_DISABLE_EXPLICIT_SYNC=1`.
- NVIDIA with X11 or Hyprland: `WEBKIT_DISABLE_DMABUF_RENDERER=1`.

Detection: `/sys/class/drm` vendor `0x10de` and the bound driver; session from `GDK_BACKEND`,
then `XDG_SESSION_TYPE`, then `WAYLAND_DISPLAY`/`DISPLAY`. We write this ourselves (about 60
lines) from the variables documented in Tauri's Linux graphics guide. A crate named
`webkit2gtk-nvidia-quirk` reportedly does the same; we have not verified it and do not depend
on it. If we ever copy from it, its MIT notice goes into the third-party notices.

- A `--safe-gpu` flag and a Settings switch force the slowest, safest path
  (`WEBKIT_DISABLE_DMABUF_RENDERER=1` and `WEBKIT_DISABLE_COMPOSITING_MODE=1`).
- The variables we add are remembered. Programs the app starts (file manager, browser, the
  CLI worker) get the original environment without them.
- The CLI is a separate binary and never sets or needs any of this.

The AppImage can crash on Arch-based systems because of bundled `libwayland` libraries. The
AUR package is the recommended install there; the AppImage is tested on CachyOS before each
release.

### 10.5 `doctor`

Prints, and returns in `--json`: installs and channels found and how; path casing, duplicate
entries that differ only in case, and symlinks on the two target paths; whether the target
folder is writable; BOM and line endings of the loose `global.ini`; the game language line;
traces of other tools; GPU and session detection; app directories; interrupted applies;
patch states. It changes nothing.

Traces of other tools it reports, all present on our machine today:

- a `Frontend_PU_Version` stamp from Smart Citizen;
- `.starstrings_version`, and stray `LIVE/Files`, `LIVE/Industries`, `LIVE/Space` folders
  left by an old updater that split the path at its spaces;
- an **empty `Data/languages.ini`** (0 bytes) that Smart Citizen copied over the game's.
  We never write that file. Whether an empty one harms anything once Smart Citizen's text is
  gone is checked in game in M1; until then `doctor` reports it and suggests the launcher's
  "Verify files".

### 10.6 Is the game running?

- **Windows:** process list; `StarCitizen.exe` whose image path is inside the channel folder.
- **Linux:** the game is a Wine process, and its command line holds a *Windows* path such as
  `C:\...\StarCitizen\LIVE\Bin64\StarCitizen.exe`. For each `/proc/<pid>/cmdline` whose first
  argument ends in `StarCitizen.exe` (split on both `\` and `/`, case ignored):
  - channel = the path part before `Bin64`;
  - prefix = `WINEPREFIX` from `/proc/<pid>/environ`, canonicalised and compared with the
    install's prefix.
  - If the environment cannot be read or the path cannot be parsed, the game counts as
    running for **every** channel. Wrongly skipping an apply is the safe mistake.
- `RSI Launcher.exe` is found the same way and only produces a warning.

## 11. Security, hardening and network policy

### Network

- **Off by default.** After a fresh install, StarOrg Strings' own code makes no network
  request. Each network feature has its own switch and its own wording of what is contacted:
  1. **Check for updates** (v1): one request to the release endpoint.
  2. **Use published game data** (addendum; v1 per Q17): downloads datasets for the installed build
     from `voidput/sc-gamedata-dumps`, verified by checksum, parsed as data only.
- The CLI has no HTTP client in v1 (CI checks the dependency tree). When feature 2 arrives it
  obeys the same switch; with the switch off the CLI always extracts locally.
- No telemetry, crash upload or analytics exists in the code.
- **What we do not control.** On Windows the window is drawn by Microsoft's WebView2 runtime,
  which has its own update and service traffic. We turn off what the runtime lets an app turn
  off and say so plainly in Settings → Network. On Linux, WebKitGTK loads only our bundled
  pages. The Windows installer downloads the WebView2 runtime if it is missing (section 2).

### Tauri

- Strict CSP: `default-src 'self'`; no remote scripts, styles, fonts or images; no `eval`.
- Capabilities list only what the UI needs: dialog (folder picker), opener restricted to the
  app's own directories, updater. No shell plugin, no generic filesystem plugin, no HTTP
  plugin.
- The webview never receives a raw path it can write to. All file work goes through typed
  commands that take a channel id, an enum or a key, and resolve paths in Rust.
- No remote URL is ever loaded in the window.

### File safety

- Writes go to exactly these places: the `global.ini` and `user.cfg` of a set-up channel, and
  our own app directories.
- **Symlinks** are followed and the real file is edited in place; a link is never replaced by
  a file (section 7.4). The real target must be a regular file owned by the current user.
  Paths are canonicalised before use and shown to the user when they leave the channel folder.
- All writes are atomic (temp file beside the real target, fsync, rename, folder fsync).
- The app never runs as root or elevated and refuses to apply if it is.
- Locks are OS advisory locks, never "a file exists".
- Input limits: patch files 256 KiB, overrides 8 MiB, `build_manifest.id` 64 KiB, launcher
  log tail 4 MiB, stock ini 64 MiB, DCB 2 GiB. Oversized input is rejected, not truncated.
- Patch, profile and override files are data. Nothing in them is executed, and patch fields
  are limited to the documented set. `replace` is plain text, not a regular expression.
- Game data is untrusted input: extraction runs in a separate process (section 3.3), cache
  files are hash-checked on load, and validation (section 7.3) runs on our own output before
  it reaches the game.
- **Diagnostics exports** replace: the home directory with `~`; the Windows user name in
  `C:\Users\<name>` and in `drive_c/users/<name>` with `<user>`; the Wine prefix path with
  `<prefix>`; and the install root with `<install>`, so mount layout does not leak.

### Supply chain

- `Cargo.lock` and the UI lockfile are committed; CI builds with `--locked` and a frozen
  lockfile.
- StarBreaker is pinned by commit, from our mirror. `cargo deny`'s sources check allows
  exactly that git URL and no other.
- `cargo deny` (licences, advisories, sources) and `cargo audit` run in CI.
- GitHub Actions are pinned by commit SHA; Dependabot keeps them current.
- Releases carry `SHA256SUMS`, signed with our release key, and build provenance attestations.
- The updater verifies a signature made with our key before installing anything.

### Licences and notices

- **Our own licence is not chosen yet** (Q20). Until it is, the source is private and all
  rights are reserved; binaries are free to use.
- The About screen and a `THIRD-PARTY-NOTICES` file in every package are **generated**
  (`cargo about` for Rust, a licence report for npm) and cover every dependency, including
  the Tauri stack. CI fails on a licence that is not on the allow list.
- Named credits: StarBreaker (full MIT text), Smart Citizen (ideas), fonts (OFL). The AppImage
  bundles WebKitGTK and GTK, which are LGPL: their notices and a link to source go in the
  same file.
- Shown in About and in the README: "StarOrg Strings is an unofficial fan-made tool. It is
  not affiliated with or endorsed by Cloud Imperium Games or Roberts Space Industries. Star
  Citizen is a trademark of its owners."
- **Smart Citizen clean-room rule.** Smart Citizen is Apache-2.0 and ships a NOTICE file.
  "Ideas only" holds as long as code is written from this spec. People implementing a feature
  do not open Smart Citizen's source for it. The parity script (section 13) compares only the
  *numbers* in the two tools' output files. If anything is ever derived from its code, that
  file is marked, and Smart Citizen's licence and NOTICE are shipped with it.

A review of CitizenHex's `smart-citizen-hardenedSEC` for further ideas is still to be done

## 12. Release, CI, versioning, updater

### Where releases live (decide by the end of M0, Q1)

The source repo is private. A private repo's release assets need a GitHub login, which breaks
all of these at once:

| Thing | Why it needs a public location |
|---|---|
| In-app updater | Fetches `latest.json` and the installer without credentials. The URL and public key are baked into v0.1.0 |
| "New version exists" notice for deb/rpm/AUR | Reads the same `latest.json` |
| AUR `starorg-strings-bin` | Its PKGBUILD `source=` URL must be downloadable by anyone |
| README and website download links | Same |
| Provenance attestations | An attestation made in a private repo cannot be verified by the public |
| M4 acceptance ("a prerelease updates itself") | Cannot pass without it |

Options: **(a)** a public `voidput/starorg-strings-releases` repo that CI publishes to
(binaries, `latest.json`, `SHA256SUMS`, PKGBUILD, install notes; no source); **(b)** static
hosting on starorg.tools; **(c)** make the source repo public. This spec assumes (a).

Option (c) stays open for later because **no CIG prose is ever committed**: fixtures use
made-up prose, snapshots hold only our own generated text, and patch guards are hashes
(sections 4.5 and 13). That rule applies from the first commit, private or not.

### Versioning

- Semver. One version, in `[workspace.package]` of the root `Cargo.toml`. `tauri.conf.json`
  omits `version` so Tauri reads the crate's. `app/package.json` is bumped alongside.
- Tags are `vX.Y.Z`. Before 1.0, breaking changes bump the minor.
- Conventional commits; release-please opens the release PR. No AI attribution in commits or
  PR text.
- Two things are known weak spots and are proven in **M0**, not M4, with a throwaway
  `v0.0.1` release: that release-please (`release-type: rust`) bumps the workspace version,
  `app/package.json` and `Cargo.lock` together; and that Tauri resolves a version inherited
  with `version.workspace = true`.

### Workflows (modelled on rsi-plus)

- **`ci.yml`** (pull requests and pushes): `cargo fmt --check`, `cargo clippy -D warnings`,
  `cargo test --workspace --locked` on Ubuntu and Windows, plus the release-mode worker panic
  test; the Windows apply tests on a synthetic install tree (section 13); the `cargo tree`
  checks (no GTK/HTTP in the CLI); UI lint, type check and unit tests; `cargo deny`; a CLI
  smoke test (`build` against the recorded fixture); docs frontmatter check.
- **`release.yml`** (push to `main`):
  1. release-please.
  2. On `release_created`: build matrix `ubuntu-22.04` and `windows-latest`,
     `fail-fast: false`, with `tauri-action`, `updaterJsonPreferNsis: true`; the static musl
     CLI build; the Windows portable zip.
  3. Generate third-party notices; attest each artifact; a checksum job writes, signs and
     uploads `SHA256SUMS`.
  4. Publish to the public release location. The release stays a draft until all assets are
     attached.
- **`prerelease.yml`** (push to `dev`): `vX.Y.Z-devNNNN` prereleases, newest 10 kept.

CI runs are watched with a small model, per house rules.

## 13. Testing strategy

### Fixtures (no CIG prose)

- **`fixtures/gamedata-<change>.json.zst`**: a `GameData` recorded from a real LIVE build. It
  contains stats and loc key names, no prose. A second one is recorded from HOTFIX, whose
  branch has an older schema.
- **`fixtures/strings-<change>.ini`**: a reduced stock-shaped file holding only the keys the
  golden tests touch. Keys, BOM, CRLF endings, flag suffixes, EM tags, `~mission()` tokens,
  format specifiers and trailing `\n` are real; the **prose between them is replaced by
  made-up filler** of the same length. It includes copies of the awkward stock shapes:
  unbalanced and nested EM tags, an open tail, format keys, a 16 KB value.
- **`fixtures/coverage-<change>.json`**: the coverage report of that build (below).
- A `xtask record-fixture --channel LIVE` command regenerates all three. Fixture updates are
  reviewed as diffs.
- Golden snapshots contain our generated text and the filler, never CIG's text.

### Coverage report

Every build produces it, and `--json` includes it. Per category: candidate keys, keys
written, and keys left as stock by reason (`contenders-differ`, `placeholder`, `not-in-stock`,
`format-key`, `dropped-by-validation`, `open-tail` written); plus the count of references that
matched only after case folding.

- M2 definitions: a **candidate** is a key some record has text for (a record whose block
  would be empty, such as a thruster with one common line, is no candidate). Two more
  reasons exist: `collision` (two stock keys fold to the key, section 4.3) and
  `owned-by-other` (an earlier generator already writes the key). Categories:
  `ships`, `components`, `ship-weapons`, `fps-weapons`, `missiles`, `component-tags`,
  `ship-weapon-tags`, `missile-tags`, `mission-titles`, `mission-descriptions`, `branding`.
- Baselines live in `fixtures/coverage-<change>.json` (counts only, no keys). The
  ignored test `starorg-data/tests/enhance_real.rs` builds every installed channel and
  checks them; until the recorded `GameData` fixture exists the check needs a game install.

- The recorded report is the baseline. A CI test fails when a category's written count falls
  more than 2% below the baseline without the baseline being updated in the same change.
- This is how a schema change that silently empties a category, or a namesake rule that
  leaves too much as stock, becomes visible.

### Layers

| Layer | What it proves |
|---|---|

### Parity checks against Smart Citizen

Parity is checked only where the underlying number should be the same. A local-only script
compares the numbers in our output with those in a Smart Citizen output file and reports
differences for review; it is not a CI gate and reads no Smart Citizen code (section 11).

- **Expected to match:** shield HP and regen, quantum drive speed and spool, power output,
  cooling rate, missile damage and lock range, component HP, EM/IR, ship SCM and max speed,
  blueprint lists per mission (as sets).
- **Expected to differ, by design:** fire modes and fire rate; pitch/roll/yaw (present in
  ours); ship guns and loadout; placeholder overheat and zero-value lines (absent in ours);
  key spelling (`,P` kept) and line endings; bullet order; mission tags computed over all

## 15. Risks

### 15.1 Project risks

| Risk | Effect | Mitigation |
|---|---|---|
| Private repo vs anything public | Updater, AUR, download links and update notices all fail | Release location decided in M0 (Q1); public releases repo assumed |
| Updater key lost | No more updates for existing installs | Key in 1Password and CI secrets from day one |
| StarBreaker has one maintainer and no versioning promise | A rev bump can break the build; a force-push or deletion can break reproducible builds | Our mirror; pin by commit; one adapter crate; pinned toolchain; `--locked` |
| `parse_entries` stops silently | Missing entries or a stale DataCore after a game patch | Our own count reader; require both files; CRC check; opt-in strict mode proposed upstream |
| DataCore schema changes between patches or branches | Stats disappear quietly | Schema-drift warnings; exit code 5; coverage baseline; integration test on every installed channel |
| Bad game data crashes or exhausts memory | App or launch hook dies | Extraction in a child process; size caps; `panic = "unwind"` pinned and tested |
| `user.cfg` is a shared symlink (true on our machine) | Refused apply, or a link silently replaced by a file | Follow links, edit in place, lock by real path, write nothing when the line is right |
| Restore overwrites user settings or brings back a stale table | Lost settings; raw `@keys` after a patch | We track one line, never the file; "back to stock" deletes our file; foreign restore is build-checked |
| Switching a non-English player to English | Game language changes without consent | Guard with explicit opt-in; never from a hook |
| Stock text is not clean (unbalanced tags, `%`) | Strict validation would block every apply | Compare with stock; drop single edits; format keys are off limits |
| Crash between write and record | Our own file later counted as foreign | Journal; `outputs.json` |
| Prefix moved or drive letter changed | Profile and backups orphaned | Random install id; re-link |
| Stale or torn cache | Wrong model or a corrupt base written to the game | Cache key includes schema and StarBreaker commit; hashes checked on load; atomic write |
| Case-sensitive writes on Linux | Duplicate `data/` or `user.cfg`; undefined game behaviour | `resolve_ci`; duplicate detection; apply tests on a cased tree |
| Missing BOM | Every string shows as `@key` | Byte-level check before write |
| Writing while the game or launcher is patching | Corrupt or overwritten file | Process guard (Wine-aware), p4k stability check, locks |
| Launcher patches after the pre-launch hook ran | First session after a patch has the previous build's text | Post-exit run; severity measured in M1; watcher later (Q5) |
| Another localization tool on the same channel | Tools overwrite each other | Detect stamps and markers; warn; `pre-existing` backup |
| Windows game folder not writable | Apply fails for default installs | Write probe; clear message with the `icacls` command; checked on a real install in M1 |
| Nobody on the team has a Windows install | Windows path untested until late | Synthetic-tree tests on the Windows runner from M1; owner named in M0 (Q19); else "beta" label |
| Unsigned Windows build | SmartScreen prompt; Smart App Control blocks outright; AV false positives | Stated plainly; signed checksums; portable zip; signing decision before 1.0 (Q3) |
| WebKitGTK on NVIDIA/Wayland | Blank window | Env quirk before window creation; `--safe-gpu`; lite effects by default |
| AppImage on Arch-based systems | Crash at start | AUR package recommended; AppImage tested on CachyOS |
| Atomic Linux systems can only use the AppImage | No CLI on `PATH` for hooks | CLI tarball; "Install command-line tool" |
| 91,000-row table in a webview | UI hangs | Real virtualisation, lazy tooltips, backend-side filtering |
| Namesake rule leaves shared keys as stock | Many items silently get no stats | Coverage report with a ceiling in M2 |
| Heuristic groupings (player-hull filter, placeholder names) | Wrong or missing entries after a patch | Keep the lists small and tested; prefer leaving a key as stock over guessing |
| Mission tags depend on contract data we have not fully mapped | Wrong `[BP]` tags lead to bug reports | Conservative rules over all variants; M2a mapping; help text on limits |
| EM tags or `%` behave differently outside mobiGlas | Broken HUD text | In-game checks in M2 before defaults are fixed |
| Copying Smart Citizen too closely | Licence and identity problems | Clean-room rule; own formats; UI copy written fresh; credit given |
| M1 too large | Slips | Enhancements and the data model moved to M2; M1 is the apply core only |

### 15.2 Smart Citizen behaviours we deliberately do not reproduce

Dropping the `,P` key suffix; platform-dependent line endings; mutating the extracted cache;
syncing key variants by longest value; reading size, grade and damage type from description
text; namesake protection for description keys only; invented names for keys missing from
stock; mission info from the first variant only; tags appended after a trailing `\n`; ship
loadouts from port-name substrings; "Semi-Auto" on nearly every weapon; placeholder and zero
values printed; duplicated bomb-rack lines; ASCII-order bullet sorting; writing an empty
`languages.ini` over the game's; lower-case paths on Linux; forced watermark; backing up
`global.ini` only while also editing `user.cfg` with no way back.
